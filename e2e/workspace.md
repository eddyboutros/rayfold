# End-to-end comparison on a workspace: REST vs GraphQL vs Rayfold

Same workspace (2 organisations, 7 projects, 630 issues), same data, same flows, each stack behind real HTTP with good-practice implementations (ETags, DataLoader-style batching, Idempotency-Key convention, SSE subscriptions). Every cell is asserted by `e2e/workspace.test.ts`.

This table compares the three stacks on one workload. The rest of the end-to-end suite lives beside it: `methods.test.ts` (every HTTP method a binding serves), `security.test.ts` (the attacks of spec 12), `realdata.test.ts` (the Project Gutenberg catalogue), and `fleet.test.ts` (two servers and a real Postgres).

| Aspect | Metric | REST | GraphQL | Rayfold | Note |
|---|---|---|---|---|---|
| Board screen (6 columns, 60 issues with people and labels) | bytes for one board | 57,486 B: a purpose-built endpoint, but a resource has one representation, so every issue arrives whole (description, ids, attachments) | 21,783 B: exactly the fields asked for | 9,446 B on the binary wire (26,104 B as JSON): the same fields, named once by the server-defined view `Issue.row` | The board is the screen that hurts most: six lists in one page, each needing its own slice of the same table. |
| N+1 on the board | hand-written batching | none to wire: this endpoint was written for this screen, and it loads what it needs in one pass. The next screen needs another endpoint | 3: a DataLoader per relation. The same query and schema without them made 100 calls instead of 3 | none: a field loader is handed the whole level, so the slow version does not exist (3 calls, the same as GraphQL once its loaders are written) | Measured on this board: 100 data-source calls with the obvious GraphQL resolvers, 3 once DataLoader is added, 3 on Rayfold with nothing to add. |
| One issue with everything on its page | round trips for one issue page | 5: the issue, its comments, its sub-issues, its project, and a batch call for the two people on it | 1: one query names the whole tree | 1: one op, with the shared view `Issue.card` plus what this page adds | Bytes: REST 2,722, GraphQL 1,335, Rayfold 2,187. |
| Activity feed with four kinds of entry | how a client knows what a row is | a "type" string by convention; nothing in the contract says which fields go with which value, and a client that guesses wrong finds out at run time | an interface with inline fragments; the kind is checked by the schema | an `@interface` with `...on`; the kind is checked by the schema, and `$type` survives the compact and binary encodings | Bytes for the same 20 rows: REST 6,817, GraphQL 3,892, Rayfold 6,383. |
| Search returning three kinds of thing | bytes, same ten hits | 10,554 B: each hit wrapped in an envelope naming its kind, and each resource sent whole | 1,095 B: a union, with the fields the screen shows | 1,094 B: a union, with the fields the screen shows |  |
| Create an issue and show its page | round trips to write and then read | 2: POST /issues, then GET the new issue to load the page around it | 2: a mutation cannot feed a query in the same request, so the read is a second call | 1: the read op refers to the write op with `$ref`, and the server runs them in order |  |
| A write and the two screens that show it | round trips for a write plus two screens | 3: one for the write, one for the board, one for the feed | 2: a document is a mutation or a query, never both, so the screens follow the write | 1: writes and reads are ops of the same batch, run in order, and rows loaded for one op are not loaded again for the next | Within the request the server keeps what it loaded: the people on the board are not fetched a second time for the feed. |
| Lost update refused (two writers, one issue) | what the losing writer receives | 412 with the current representation in the body, because this endpoint was written to include it | an error with a code and the current version number; the row itself needs another request | a typed `VersionConflict` carrying the current entity in the shape the op asked for, so the client can redraw and retry without a read | All three refuse the stale write. The difference is what the client has to do next. |
| Bulk write: closing a sprint | what the client learns from the write | the new sprint state. Which of the cached issues moved is not said, so the client refetches the lists it holds | whatever the mutation selected. A mutation cannot describe rows it did not return, so the client refetches | 11 entity patches plus the sprint, in the command's own answer: every cached screen holding those issues is corrected with no further request | The sprint held 11 unfinished issues. Patches are part of every command's answer, not something the server was asked for. |
| Someone else moves an issue you are looking at | what it takes to keep one screen correct | an SSE endpoint, an event fan-out and client merge code; the event carries an id, so the client refetches (1,090 B to become correct) | a Subscription type, a resolver with an async iterator, and client merge code; then a refetch (225 B) | `live: true` on the query that already draws the screen: the server diffs the result and sends a patch, and the client cache applies it | Both other stacks can push the new state in the event itself, but then the event has to be shaped for each screen that listens. |
| A board someone else is changing | bytes per change, board open | 56,628 B: the event carries an id, so the client fetches all six columns again | 21,529 B: the subscription carries the event, so the client runs the board query again | 692 B: the server diffs the board it already served and sends the row that moved and the two counts that changed | The client asks for nothing: it holds one live query, and what a change costs depends on the change rather than on the size of the screen. |
| One tenant rule, every way in | surfaces one rule covers | 1: the handler it was written in. A second endpoint over the same rows needs the check written again, and nothing fails if it is forgotten | 1: the resolver it was written in. The schema cannot carry the rule, so every new resolver repeats it | 4: the batch endpoint, the `GET /issues/{id}` route bound with `@http`, the MCP resource an assistant reads, and the live query all refuse the same row from one `@allow` on the entity | Authorization written by hand for the rules asserted here: 22 lines in the REST stack and 27 in the GraphQL stack, against 15 declarations in the Rayfold schema. All three refuse this cross-tenant read; the difference is how many places have to stay correct as the API grows. |
| An expensive request from a client | what stops a costly request | 1: the endpoint decides its own shape, so the client cannot ask for a deeper join (the same reason it cannot ask for less) | 0: the query ran and returned 37,492 bytes; cost analysis is a separate library to add and tune | 1: the cost of 81,006 was computed from the schema against a budget of 1,000 and refused, with no loader called | Rayfold charges rows and loads, not columns: a page costs its size, and scalar fields are free. |
| Second read of an unchanged screen | conditional requests | 304, with the cache rule written into the handler | 304, because this server was configured to allow GET for queries; most GraphQL deployments POST everything and cannot | 304, with `private, max-age=60` taken from `@cache(maxAge: 60s, scope: public)` on the entity, and the shape in the URL so the key is stable |  |
| One flaky field, the rest of the page fine | where 'this field may fail' is written | in the handler, plus a `warnings` array the client has to know about; nothing in the contract says the field is unreliable | in the resolver; the field is nullable like every other nullable field, so a client cannot tell a missing value from a broken integration | `@partial` on the field: the frame carries the rest of the data and an error entry with the field's path, and generated clients see it | All three kept the page. The difference is whether the client can know in advance which fields are allowed to be missing. |
| A slow or large field on a page | delivery of a slow field | the description is part of the issue resource, so it is sent every time, even to a list that never shows it | one body: the client waits for the slowest field it asked for (`@defer` is still not in graphql-js 17) | `@lazy` on the field: the frame with the page comes first, the description follows at its path in the same response |  |
| Letting an AI assistant use the API | work to expose typed tools with dry runs | an OpenAPI document to write and keep true, plus an adapter; no dry run | introspection plus custom glue to turn mutations into tools; no dry run | none: 28 tools listed at /mcp from the same schema, with typed input, typed errors, and `simulate` to try a command without writing |  |
